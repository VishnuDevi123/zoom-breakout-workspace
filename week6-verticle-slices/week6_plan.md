# Week 6 - Activity system

Goal: the host attaches structured activities to a round, and participants
work on them together in their room. Activities exist to get people
interacting; host-side results are not part of this week.

## Slices

| # | Slice | Owner | State |
| --- | --- | --- | --- |
| 1 | Activity definitions inside the task record | backend (human) | open |
| 2 | Host activity editor on the task page and the live panel | frontend, ~220 lines | open |
| 3 | Response store and routes, `roomRevisions` on the stream | backend (human) | open |
| 4 | Participant activities in the room page's middle column | frontend, ~300 lines | open |
| 5 | Change and removal toasts for participants and host | frontend, ~60 lines | open |

## Zoom

Not involved. No SDK call, capability or webhook is added. Participant
identity is the `participantUUID` the app already has, and the room comes from
the host's saved draft, as in week 5.

There is no sign-in, so the backend trusts the `participantUUID` a client sends.
Individual answers are hidden from other participants by the server's filter,
not locked: a client that fakes an id could read them.

## Activity types

Three kinds, one discriminated union. Every kind has a host-written headline and
a free-text `details` field for a clue or a longer description.

```ts
type Activity =
  | { kind: "individual"; id: string; question: string; details: string }
  | { kind: "ideaBoard"; id: string; question: string; details: string }
  | { kind: "checklist"; id: string; title: string; items: ChecklistItem[] };

interface ChecklistItem { id: string; label: string }
```

- **Individual response.** Each participant writes one private answer. Only
  the author sees it on the participant side.
- **Idea board.** Sticky notes, as on a Figma board. A note has a title and a
  description, shows who added it, and its author can edit or remove it.
- **Shared checklist.** The host lists items; anyone in the room can tick or
  untick any item.

Voting is out of scope.

## Slice 1 - definitions in the task record

`RoundTasks` gains `activities: Activity[]`, round-wide rather than per room.
Definitions are host-authored and edited on the same page as the task, so they
reuse the task route, its revision check and the `taskRevision` push instead of
adding a store.

`store/tasks.ts` validates the union: known `kind`, non-empty headline, string
`details`, unique ids, a bounded number of activities and checklist items.
Ids are generated by the client, like room ids in drafts.

## Slice 3 - responses

New `store/responses.ts`, keyed `(parentUUID, roundId, roomId)`. It cannot live
in the task store: participants write it, and the key needs the room.

```ts
interface RoomResponses {
  answers: Record<activityId, Record<participantUUID, { text: string }>>;
  ideas: Record<activityId, IdeaNote[]>;
  ticks: Record<activityId, Record<itemId, { participantUUID: string; name: string }>>;
}

interface IdeaNote { id: string; participantUUID: string; name: string; title: string; description: string }
```

- Individual answer: saving again replaces it.
- Idea notes: add, edit or remove one note at a time, never replace the whole
  board, so two people typing at once never overwrite each other. Only the
  author may edit or remove a note.
- Checklist: one tick per item; the latest click wins.
- The author's display name is stored with the note or tick when written, so it
  survives the person leaving the meeting.
- Every write checks the activity still exists in the round's task record with
  the matching kind; a write to a removed activity is rejected.

Routes, under `/api/responses/:roundId/rooms/:roomId`:

- `GET ?parentUUID=&participantUUID=` - the room's notes and ticks, plus only
  the caller's own individual answers.
- `PUT .../answers/:activityId` - save or replace my answer.
- `POST .../ideas/:activityId`, `PUT` and `DELETE .../ideas/:activityId/:noteId`.
- `PUT .../ticks/:activityId/:itemId` - body `{ done }`.

Live refresh: `LiveState` gains `roomRevisions: Record<roomId, number>`. Every
response write bumps that room's counter and notifies the stream. Clients
refetch only when their own room's counter moves. The stream carries counters,
never content, so nothing leaks between rooms and `subscribe()` needs no room
scoping. This settles the open transport point from week 5.

## Mid-round changes

The host can change activities during a round through `EditTaskModal`.

- **Edit** (question, details, title, checklist item labels): participants'
  responses are kept. Participants get a toast asking them to review their
  answers against the change.
- **Delete an activity**: the task save removes it, and `store/tasks.ts` calls
  `deleteActivityResponses` so every room's answers, notes and ticks for it are
  removed in the backend at once. No orphan responses remain. Participants and
  the host each get a toast.
- **Delete a checklist item**: its tick is removed with it, by the same call.

Participants tell an edit from a removal by comparing activity ids before and
after the refetch.

## Deliberately not built

Host results view, voting, per-room activity overrides, reordering by drag,
exporting responses, SQLite (still after week 7). Deleting a round removes its
responses along with its tasks.
